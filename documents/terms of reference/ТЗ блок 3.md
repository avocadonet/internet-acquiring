# Техническое задание: Модуль Payment Gateway & 54-ФЗ (Платежный контур Т-Банка)

Документ представляет собой полную инженерную спецификацию модуля **Payment Gateway & 54-ФЗ** для реализации разработчиком в рамках архитектуры модульного монолита `reklama-bot-platform`.

---

## 1. Паспорт модуля и границы ответственности

* **Идентификатор модуля:** `payment_gateway`
* **Расположение в репозитории:** `src/modules/payment_gateway/`
* **Точка монтирования контрактов:** `src/shared/contracts/payments.py`
* **Точка запуска рантайма:** `src/apps/api_runner.py` (FastAPI Webhook Server)

### 1.1. Входит в зону ответственности (In-Scope)

1. Реализация асинхронного HTTP-клиента к API эквайринга Т-Банка v2 (`/v2/Init`, `/v2/Cancel`, `/v2/GetState`).
2. Построение фискального чека по требованиям 54-ФЗ (массив `Receipt.Items`, системы налогообложения, НДС, признаки способа и предмета расчета).
3. Математически корректный алгоритм генерации и сверки цифровой подписи (`Token`) по протоколу Т-Банка (SHA-256) с фильтрацией `None`, обработкой `bool` и сортировкой ключей.
4. Предоставление FastAPI-эндпоинта для приема входящих Webhook-уведомлений от банка.
5. Двухфакторная валидация подлинности вебхука: обязательная сверка `TerminalKey` и проверка криптографической подписи `Token`.
6. Вызов внутреннего контракта `IOrderInternalService.handle_payment_succeeded` при получении статуса `CONFIRMED`.
7. Реализация метода выполнения отмены/возврата средств (`cancel_payment`) для вызова из модуля компенсаций.

### 1.2. НЕ входит в зону ответственности (Out-of-Scope)

* Взаимодействие с пользователем Telegram и FSM-сценарии (зона ответственности `bot_ingress`).
* Управление жизненным циклом и статусами сущностей `orders` в БД (зона ответственности `order_domain`).
* Планирование очередей задач и выборка `FOR UPDATE SKIP LOCKED` (зона ответственности `outbox_engine`).
* Непосредственная выгрузка контента в каналы (зона ответственности `channel_publisher`).

Базовый URL тестового окружения: `[https://rest-api-test.tinkoff.ru/v2/](https://rest-api-test.tinkoff.ru/v2/)`

### 4.1. Алгоритм генерации токена (SHA-256 Signature)

Протокол эквайринга Т-Банка требует подписания запросов и проверки входящих вебхуков. Ошибки при сериализации приводят к отказам `403 Signature Mismatch`.

#### Правила формирования строки подписи

1. Исключить служебные поля: `Token`, `Receipt`, `DATA`, `Shops`.
2. Исключить ключи, значения которых равны `None` или `null` (строка `"None"` ломает хеш).
3. Исключить составные объекты: вложенные словари (`dict`) и массивы (`list`).
4. Привести булевы значения строго к нижнему регистру: `True` -> `"true"`, `False` -> `"false"`.
5. Добавить пару ключ-значение: `Password: <Секретный пароль терминала>`.
6. Отсортировать словарь по ключам в лексикографическом порядке (алфавитном).
7. Склеить только **значения** отсортированного словаря в одну непрерывную строку без разделителей.
8. Вычислить SHA-256 хеш полученной строки в шестнадцатеричном формате (hex lowercase).

#### Реализация алгоритма (`hasher.py`)

```python
import hashlib
from typing import Any


def generate_tbank_token(payload: dict[str, Any], secret_password: str) -> str:
    flat_params: dict[str, str] = {}
    excluded_keys = {"Token", "Receipt", "DATA", "Shops"}

    for key, value in payload.items():
        if key in excluded_keys or value is None:
            continue
        if isinstance(value, (dict, list)):
            continue

        if isinstance(value, bool):
            flat_params[key] = "true" if value else "false"
        else:
            flat_params[key] = str(value)

    flat_params["Password"] = secret_password

    # Лексикографическая сортировка ключей
    sorted_keys = sorted(flat_params.keys())
    raw_signature = "".join(flat_params[k] for k in sorted_keys)

    return hashlib.sha256(raw_signature.encode("utf-8")).hexdigest()

```

### 4.2. Инициализация платежа (`POST /v2/Init`)

Метод вызывается при оформлении заказа. Обязан содержать блок `Receipt` в полном соответствии с форматом фискализации 54-ФЗ.

#### Структура запроса к банку

```json
{
  "TerminalKey": "1712345678901DEMO",
  "Amount": 150000,
  "OrderId": "7c8e9860-2621-4999-a9a3-5c02b3708e04",
  "Description": "Размещение рекламы в канале @target_channel",
  "Token": "e7b0d922bb33f6a27e...",
  "Receipt": {
    "Email": "client@example.com",
    "Phone": "+79991234567",
    "Taxation": "usn_income",
    "Items": [
      {
        "Name": "Размещение рекламного сообщения",
        "Price": 150000,
        "Quantity": 1.00,
        "Amount": 150000,
        "PaymentMethod": "full_payment",
        "PaymentObject": "service",
        "Tax": "none"
      }
    ]
  }
}

```

#### Требования к блоку 54-ФЗ (`Receipt.Items`)

* `Taxation` конфигурируется через переменные окружения (`osn`, `usn_income`, `usn_income_outcome`, `patent`, `esn`).
* В `Receipt` обязательно должно присутствовать хотя бы одно поле: `Email` или `Phone` (в формате E.164: `+7XXXXXXXXXX`). Если переданы оба — передавать оба.
* `Items`:
* `Name`: Ограничение длины до 128 символов.
* `Price`: Цена позиции в копейках.
* `Quantity`: Количество (передавать с плавающей точкой: `1.00`).
* `Amount`: Стоимость позиции в копейках (`Price * Quantity`).
* `PaymentMethod`: `full_payment` (Полный расчет).
* `PaymentObject`: `service` (Услуга).
* `Tax`: Ставка НДС (`none` — без НДС; конфигурируется в `.env`).

#### Формат запроса

```json

  "PaymentId": "3485720194",
```

* Если `Amount` не передан, банк производит отмену на всю исходную сумму авторизации.
* Токен рассчитывается по правилам раздела 4.1 для переданных полей (`TerminalKey`, `PaymentId`, `Amount` (если передан), `Password`).

## 5. Webhook Ingress (Прием уведомлений от эквайринга)

Серверная точка входа для асинхронных уведомлений Т-Банка.

### 5.1. Маршрут и сетевые требования

* **URL:** `POST /api/v1/payments/tbank/webhook`
* **Таймаут ответа:** Банк ожидает ответ не более чем за 5 секунд. При превышении таймаута банк считает доставку неудачной и инициирует повторы по экспоненциальной шкале.
* **Формат успешного ответа:** Строго строка `OK` в теле ответа (Content-Type: `text/plain`) со статусом HTTP `200`. Ответ в формате JSON `{"status": "ok"}` банком **не принимается**.

### 5.2. Двухфакторная валидация безопасности (Security Layer)

Входящий запрос обязан проходить валидацию в строгом порядке:

```
[Входящий POST-запрос]
         │
         ▼
[Шаг 1: Проверка TerminalKey] ──(Не совпадает с конфигурацией)──> HTTP 403 Forbidden
         │ (Совпадает)
         ▼
[Шаг 2: Расчет SHA-256 Token]
         │
         ▼
[Шаг 3: Сверка подписи] ───────(Хеш не равен webhook.Token)─────> HTTP 400 Bad Request
         │ (Хеш валиден)
         ▼
[Шаг 4: Обработка статуса]

```

1. **Проверка терминала:** Сверка `payload.get("TerminalKey") == config.TBANK_TERMINAL_KEY`. Предотвращает эксплуатацию уязвимости с подменой терминала злоумышленником.
2. **Проверка подписи:** Вызов `generate_tbank_token(payload, config.TBANK_SECRET_PASSWORD)` и сравнение с `payload.get("Token")`. При несовпадении запрос немедленно отвергается.

### 5.3. Обработка событий и вызов доменного слоя

* **Интересующий статус:** `Status == "CONFIRMED"` (средства успешно списаны / заблокированы).
* При получении `CONFIRMED`:
1. Извлечь `OrderId` (UUID заказа) и `PaymentId`.
2. Передать данные в `IOrderInternalService.handle_payment_succeeded(order_id, payment_id)`.
3. Вернуть `Response(content="OK", media_type="text/plain", status_code=200)`.


* **Другие статусы (`AUTHORIZED`, `REJECTED`, `REFUNDED`):**
* Логируются на уровне `INFO`.
* Возвращается HTTP 200 `OK` без побочных эффектов.

## 7. Эталонная реализация ключевых узлов

### 7.1. Билдер чека 54-ФЗ (`receipt.py`)

```python
from typing import Any
from src.shared.contracts.orders import CustomerContactDTO


class ReceiptBuilder:
    def __init__(self, taxation: str, default_tax: str = "none"):
        self.taxation = taxation
        self.default_tax = default_tax

    def build_receipt(
        self, amount_kopecks: int, description: str, contact: CustomerContactDTO
    ) -> dict[str, Any]:
        if not contact.email and not contact.phone:
            raise ValueError("Для формирования чека 54-ФЗ требуется Email или Phone")

        receipt: dict[str, Any] = {
            "Taxation": self.taxation,
            "Items": [
                {
                    "Name": description[:128],
                    "Price": amount_kopecks,
                    "Quantity": 1.00,
                    "Amount": amount_kopecks,
                    "PaymentMethod": "full_payment",
                    "PaymentObject": "service",
                    "Tax": self.default_tax,
                }
            ],
        }

        if contact.email:
            receipt["Email"] = contact.email
        if contact.phone:
            receipt["Phone"] = contact.phone

        return receipt

```

### 7.2. FastAPI Webhook Router (`routers/webhook_router.py`)

```python
import logging
import uuid
from typing import Any
from fastapi import APIRouter, Depends, Header, HTTPException, Request, Response, status
from src.modules.payment_gateway.config import PaymentGatewayConfig
from src.modules.payment_gateway.hasher import generate_tbank_token
from src.shared.contracts.orders import IOrderInternalService

logger = logging.getLogger(__name__)
router = APIRouter(prefix="/api/v1/payments/tbank", tags=["Payments Webhook"])


@router.post("/webhook")
async def handle_tbank_webhook(
    request: Request,
    config: PaymentGatewayConfig = Depends(),
    order_service: IOrderInternalService = Depends(),
) -> Response:
    try:
        payload: dict[str, Any] = await request.json()
    except Exception:
        raise HTTPException(status_code=status.HTTP_400_BAD_REQUEST, detail="Invalid JSON")

    # 1. Проверка TerminalKey
    terminal_key = payload.get("TerminalKey")
    if terminal_key != config.TBANK_TERMINAL_KEY:
        logger.warning("Отклонен вебхук с некорректным TerminalKey: %s", terminal_key)
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN, detail="TerminalKey mismatch"
        )

    # 2. Проверка цифровой подписи (Token)
    received_token = payload.get("Token")
    expected_token = generate_tbank_token(payload, config.TBANK_SECRET_PASSWORD)

    if received_token != expected_token:
        logger.error("Ошибка подписи вебхука Т-Банка. Ожидалось %s, получено %s", expected_token, received_token)
        raise HTTPException(
            status_code=status.HTTP_400_BAD_REQUEST, detail="Invalid token signature"
        )

    # 3. Маршрутизация статуса
    payment_status = payload.get("Status")
    order_id_raw = payload.get("OrderId")
    payment_id = str(payload.get("PaymentId"))

    logger.info(
        "Получен валидный вебхук Т-Банка: OrderId=%s, Status=%s, PaymentId=%s",
        order_id_raw,
        payment_status,
        payment_id,
    )

    if payment_status == "CONFIRMED":
        if not order_id_raw:
            logger.error("Вебхук со статусом CONFIRMED не содержит OrderId")
            return Response(content="OK", media_type="text/plain", status_code=200)

        try:
            order_id = uuid.UUID(order_id_raw)
            await order_service.handle_payment_succeeded(order_id, payment_id)
        except Exception as e:
            logger.exception("Ошибка при обработке успешного платежа в домене: %s", e)
            # Возвращаем 500, чтобы банк повторил доставку, если произошел транзиентный сбой БД
            raise HTTPException(
                status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
                detail="Domain processing failure",
            )

    return Response(content="OK", media_type="text/plain", status_code=200)

```

## 8. Граничные сценарии и отказоустойчивость

| Инцидент / Граничное состояние | Поведение модуля | Решение / Защита |
| --- | --- | --- |
| **Поддельный вебхук с тестового терминала** | Злоумышленник регистрирует свой мерчант и шлет валидно подписанный вебхук на наш URL. | Жесткая проверка `TerminalKey` до расчета хеша. Если ключ не равен нашему — моментальный отказ `403`. |
| **Сетевой таймаут HTTP-клиента при вызове `/v2/Init**` | Банк не ответил за 10 секунд (сетевой лаг, сбой шлюза). | Настройка `httpx.Timeout(connect=5.0, read=10.0, write=5.0)`. Проброс доменного `PaymentGatewayTimeoutError` для корректного сообщения пользователю. |
| **Дублирование вебхуков (At-least-once)** | Банк шлет повторный вебхук `CONFIRMED` через 10 секунд из-за кратковременной задержки ответа. | Модуль валидирует подпись и передает запрос в `order_service`. Идемпотентность гарантируется на уровне `order_domain`. Вебхук получает `OK`. |
| **Пустые поля со значением `None` в ответе/запросе** | В словаре запроса присутствуют необязательные поля со значением `None`. | Функция `generate_tbank_token` безусловно отфильтровывает все пары, где `value is None`, исключая поломку конкатенации строки подписи. |
| **Булевы флаги в теле запроса** | Параметры вроде `FailMtid: True` приводят к строке `"True"`. | Принудительное приведение `bool` строго к `"true"` / `"false"` в нижнем регистре. |
