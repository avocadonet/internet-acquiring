# Техническое задание: Модуль Compensation & Incident Management (Контур компенсаций и возвратов)

Документ представляет собой полную инженерную спецификацию модуля **Compensation & Incident Management** для реализации разработчиком в рамках архитектуры модульного монолита `reklama-bot-platform`.

---

## 1. Паспорт модуля и границы ответственности

* **Идентификатор модуля:** `compensation`
* **Расположение в репозитории:** `src/modules/compensation/`
* **Точка монтирования контрактов:** `src/shared/contracts/outbox.py`, `src/shared/contracts/payments.py`, `src/shared/contracts/orders.py`
* **Рантайм-окружение:** Запускается внутри процесса `src/apps/worker_runner.py` как зарегистрированный обработчик задач `OutboxTaskType.EXECUTE_PAYMENT_REFUND` и фоновый сервис мониторинга инцидентов (DLQ).

### 1.1. Входит в зону ответственности (In-Scope)

1. Реализация контракта `IOutboxTaskHandler` для типа задачи `OutboxTaskType.EXECUTE_PAYMENT_REFUND`.
2. Вызов клиента эквайринга `IPaymentClient.cancel_payment()` (метод `/v2/Cancel` Т-Банка) для возврата холдированных или списанных средств заказчику.
3. Фиксация результата возврата в доменном слое через вызов `IOrderInternalService.handle_refund_succeeded()`.
4. Отправка сервисного уведомления покупателю в Telegram о срыве публикации и успешном оформлении возврата средств.
5. **Dead Letter Queue (DLQ) & Incident Management:**
* Автоматический мониторинг задач с флагом `failed_permanently = TRUE`.
* Формирование и отправка структурированных алертов дежурному администратору в служебный Telegram-канал/чат мониторинга.
* Фиксация инцидентов, требующих ручного вмешательства (Manual Resolution Required).



### 1.2. НЕ входит в зону ответственности (Out-of-Scope)

* Низкоуровневый расчет цифровой подписи SHA-256 токена Т-Банка (зона ответственности `payment_gateway`).
* Механика выборки задач через `SELECT ... FOR UPDATE SKIP LOCKED` (зона ответственности `outbox_engine`).
* Непосредственная выгрузка контента в каналы (зона ответственности `channel_publisher`).
* Изменение первичных статусов заказов с `PENDING` на `PAID` (зона ответственности `order_domain`).

## 4. Логика выполнения компенсации (Refund Execution Flow)

### 4.1. Схема сценария отмены и возврата

```
[Outbox Worker] ──> [RefundTaskHandler.handle()]
                            │
                            ▼
               [Вызов IPaymentClient.cancel_payment()]
               (POST /v2/Cancel к API Т-Банка)
                            │
            ┌───────────────┴───────────────┐
            │                               │
     (Успех: 200 OK)                 (Ошибка API / Сеть)
            │                               │
            ▼                               ▼
 [1. handle_refund_succeeded]     [Классификация сбоя]
            │                      ├── Сеть/5xx ──> RetryableTaskError
            ▼                      └── 4xx/Отказ ──> FatalTaskError
 [2. Уведомление клиенту]                               │
            │                                           ▼
            ▼                                [on_fatal_failure]
 [3. Алерт админу: WARNING]                             │
     (Возврат выполнен)                                 ▼
                                             [Алерт админу: CRITICAL]
                                             (Требуется ручной возврат!)

```

### 4.2. Специфика протокола Т-Банка `/v2/Cancel`

* Если платеж находился в статусе `AUTHORIZED` (двухстадийная оплата / холдирование) — метод `/v2/Cancel` производит **мгновенную разблокировку** средств без комиссии.
* Если платеж находился в статусе `CONFIRMED` (одностадийное списание) — метод производит **финансовый возврат (Refund)** на карту покупателя.
* Метод идемпотентен: при повторном вызове `/v2/Cancel` по уже возвращенному платежу Т-Банк возвращает `Success: true` и статус `REFUNDED`.

## 5. Контур управления инцидентами (Incident Management & Alerts)

Система классифицирует нештатные ситуации по трем уровням критичности:

### 5.1. Уровни критичности инцидентов

| Уровень | Событие | Действие системы | Формат оповещения |
| --- | --- | --- | --- |
| `WARNING` | Публикация сорвалась, но возврат средств через банк выполнен автоматически. | Заказ переведен в `REFUNDED`, клиенту отправлено уведомление. | Информационный алерт в чат мониторинга (желтый маркер). |
| `CRITICAL` | Сбой вызова `/v2/Cancel` (недостаточно средств на счете мерчанта, блокировка терминала). | Задача ретраится до лимита, затем падает в `on_fatal_failure`. | Тревожный алерт (красный маркер): **деньги клиента зависли в системе**. |
| `FATAL` | Любая Outbox-задача перешла в `failed_permanently = TRUE` (DLQ). | Задача исключена из цикла выборки воркера. | Экстренный алерт с дампом `context.payload` и стектрейсом ошибки. |

## 7. Эталонная реализация ключевых компонентов

### 7.1. Обработчик возврата средств (`refund_handler.py`)

```python
import logging
from src.modules.compensation.alerter import TelegramIncidentAlerter
from src.modules.compensation.customer_notifier import CustomerNotifierService
from src.shared.contracts.orders import IOrderInternalService
from src.shared.contracts.outbox import (
    FatalTaskError,
    IOutboxTaskHandler,
    RetryableTaskError,
    TaskContextDTO,
)
from src.shared.contracts.payments import (
    CancelPaymentRequestDTO,
    IPaymentClient,
)
from src.shared.contracts.publishing import ExecuteRefundPayloadDTO

logger = logging.getLogger(__name__)


class RefundTaskHandler(IOutboxTaskHandler):
    def __init__(
        self,
        payment_client: IPaymentClient,
        order_service: IOrderInternalService,
        alerter: TelegramIncidentAlerter,
        customer_notifier: CustomerNotifierService,
    ):
        self.payment_client = payment_client
        self.order_service = order_service
        self.alerter = alerter
        self.customer_notifier = customer_notifier

    async def handle(self, context: TaskContextDTO) -> None:
        payload = ExecuteRefundPayloadDTO.model_validate(context.payload)
        order_id = payload.order_id
        payment_id = payload.payment_id

        logger.info(
            "Старт процедуры возврата средств по заказу %s (PaymentId: %s)",
            order_id,
            payment_id,
        )

        try:
            # 1. Вызов метода отмены/возврата эквайринга Т-Банка
            cancel_response = await self.payment_client.cancel_payment(
                CancelPaymentRequestDTO(
                    payment_id=payment_id,
                    amount_kopecks=payload.amount_kopecks,
                )
            )

            if not cancel_response.success:
                raise ValueError(f"Банк вернул статус неуспеха: {cancel_response.status}")

            # 2. Фиксация статуса REFUNDED в доменном ядре
            refund_info = {
                "payment_id": payment_id,
                "refunded_amount_kopecks": cancel_response.new_amount_kopecks,
                "bank_status": cancel_response.status,
                "reason": payload.reason,
            }
            await self.order_service.handle_refund_succeeded(
                order_id=order_id,
                refund_info=refund_info,
            )

            # 3. Информирование заказчика в боте
            await self.customer_notifier.notify_refund_completed(
                order_id=order_id,
                amount_kopecks=payload.amount_kopecks,
                reason=payload.reason,
            )

            # 4. Логирование и мягкий алерт администраторам
            await self.alerter.send_info_alert(
                title="Автоматический возврат выполнен",
                order_id=order_id,
                amount_kopecks=payload.amount_kopecks,
                reason=payload.reason,
            )

        except Exception as e:
            err_str = str(e).lower()
            # Сетевые сбои отправляем на повтор через Outbox Engine
            if "timeout" in err_str or "connect" in err_str:
                logger.warning("Сетевая ошибка при возврате заказа %s: %s", order_id, e)
                raise RetryableTaskError(f"Network error during cancel: {e}")

            # Ошибки бизнес-логики банка (недостаточно средств, отказ) переводим в фатальные
            logger.critical("Фатальный сбой при возврате заказа %s: %s", order_id, e)
            raise FatalTaskError(f"Bank refund rejected: {e}")

    async def on_fatal_failure(self, context: TaskContextDTO, error: str) -> None:
        """
        Срабатывает при исчерпании попыток или фатальном отказе банка.
        Требует немедленного привлечения дежурного инженера.
        """
        payload = ExecuteRefundPayloadDTO.model_validate(context.payload)
        logger.critical(
            "КРИТИЧЕСКИЙ ИНЦИДЕНТ: Не удалось вернуть средства по заказу %s: %s",
            payload.order_id,
            error,
        )
        await self.alerter.send_critical_alert(
            title="СБОЙ КОМПЕНСАЦИИ: ДЕНЬГИ НЕ ВОЗВРАЩЕНЫ",
            order_id=payload.order_id,
            payment_id=payload.payment_id,
            amount_kopecks=payload.amount_kopecks,
            error_message=error,
            publish_failure_reason=payload.reason,
        )

```

### 7.2. Сервис алертинга администраторов (`alerter.py`)

```python
import html
import logging
import uuid
from aiogram import Bot
from aiogram.enums import ParseMode
from src.modules.compensation.config import CompensationConfig

logger = logging.getLogger(__name__)


class TelegramIncidentAlerter:
    def __init__(self, bot: Bot, config: CompensationConfig):
        self.bot = bot
        self.chat_id = config.ADMIN_ALERT_CHAT_ID

    async def send_info_alert(
        self,
        title: str,
        order_id: uuid.UUID,
        amount_kopecks: int,
        reason: str,
    ) -> None:
        rubles = amount_kopecks / 100.0
        text = (
            f"ℹ️ <b>[INFO] {html.escape(title)}</b>\n"
            f"━━━━━━━━━━━━━━━━━━━━\n"
            f"<b>Order ID:</b> <code>{order_id}</code>\n"
            f"<b>Сумма возврата:</b> <code>{rubles:.2f} ₽</code>\n"
            f"<b>Причина отмены:</b> <i>{html.escape(reason)}</i>\n"
            f"━━━━━━━━━━━━━━━━━━━━\n"
            f"<i>Средства возвращены на карту покупателя.</i>"
        )
        await self._safe_send(text)

    async def send_critical_alert(
        self,
        title: str,
        order_id: uuid.UUID,
        payment_id: str,
        amount_kopecks: int,
        error_message: str,
        publish_failure_reason: str,
    ) -> None:
        rubles = amount_kopecks / 100.0
        text = (
            f"🚨 <b>[CRITICAL] {html.escape(title)}</b>\n"
            f"━━━━━━━━━━━━━━━━━━━━\n"
            f"<b>Order ID:</b> <code>{order_id}</code>\n"
            f"<b>Payment ID:</b> <code>{payment_id}</code>\n"
            f"<b>Сумма к возврату:</b> <code>{rubles:.2f} ₽</code>\n\n"
            f"<b>Причина сбоя публикации:</b>\n"
            f"<code>{html.escape(publish_failure_reason)}</code>\n\n"
            f"<b>Ошибка выполнения возврата:</b>\n"
            f"<code>{html.escape(error_message)}</code>\n"
            f"━━━━━━━━━━━━━━━━━━━━\n"
            f"⚠️ <b>Внимание:</b> требуется ручная отмена транзакции в ЛК Т-Бизнес!"
        )
        await self._safe_send(text)

    async def _safe_send(self, text: str) -> None:
        try:
            await self.bot.send_message(
                chat_id=self.chat_id,
                text=text,
                parse_mode=ParseMode.HTML,
            )
        except Exception as e:
            logger.critical("Не удалось отправить алерт инцидента в Telegram: %s", e)

```

## 8. Граничные сценарии и отказоустойчивость

| Инцидент | Поведение модуля | Решение / Защита |
| --- | --- | --- |
| **Отказ API банка при отмене (`Код 7: Недостаточно средств на балансе`)** | Вызов `/v2/Cancel` возвращает ошибку. | Выбрасывается `FatalTaskError`. Модуль активирует метод `on_fatal_failure`, отправляя алерт уровня `CRITICAL` с реквизитами платежа для ручного пополнения счета и возврата. |
| **Сетевой таймаут при запросе к банку** | Httpx выбрасывает `ReadTimeoutError`. | Выбрасывается `RetryableTaskError`. Движок Outbox повторяет запрос через backoff-интервал. Благодаря идемпотентности `/v2/Cancel`, повторный вызов безопасен. |
| **Бот заблокирован пользователем** | Сервис оповещения клиента не может доставить сообщение пользователю (`BotBlocked`). | Ошибка перехватывается в `CustomerNotifierService` без прерывания основной транзакции возврата. Факт блокировки логируется. |
| **Зависание задач в DLQ (`failed_permanently = TRUE`)** | Любая непредвиденная ошибка в воркере Outbox. | Фоновый инспектор `DLQService` раз в 30 минут проверяет наличие зависших задач без повторов и генерирует сводную сводку дежурным инженерам. |

## 9. Критерии приемки (Definition of Done)

1. **Архитектурная чистота:**
* Модуль взаимодействует с платежным шлюзом исключительно через контракт `IPaymentClient`.
* Модуль фиксирует результат в домене строго через метод `IOrderInternalService.handle_refund_succeeded`.


2. **Модульное тестирование (Unit Tests):**
* Тест успешного возврата: корректный вызов `cancel_payment`, перевод заказа в `REFUNDED` и отправка инфо-алерта.
* Тест обработки сетевой ошибки: при `TimeoutError` выбрасывается `RetryableTaskError`.
* Тест обработки фатальной ошибки: при бизнес-отказе банка выбрасывается `FatalTaskError` и инициируется `on_fatal_failure`.


3. **Интеграционное тестирование:**
* Проверка отправки форматированного сообщения в Telegram Test Client при вызове `alerter.send_critical_alert`.
* Проверка обработки случая, когда пользователь заблокировал бота: процесс возврата завершается успехом, ошибка нотификации подавляется.


4. **Качество кода:**
* Прохождение статического анализатора без предупреждений: `mypy --strict src/modules/compensation`.
* Полное соответствие стандартам форматирования: `ruff check src/modules/compensation`.
