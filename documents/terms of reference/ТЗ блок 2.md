# Техническое задание: Модуль Order Domain & State Machine

Документ представляет собой полную инженерную спецификацию модуля **Order Domain & State Machine** для реализации разработчиком в рамках архитектуры модульного монолита `reklama-bot-platform`.

---

## 1. Паспорт модуля и границы ответственности

* **Идентификатор модуля:** `order_domain`
* **Расположение в репозитории:** `src/modules/order_domain/`
* **Точка монтирования контрактов:** `src/shared/contracts/orders.py`, `src/shared/contracts/payments.py`, `src/shared/contracts/outbox.py`

### 1.1. Входит в зону ответственности (In-Scope)

1. Реализация доменной модели заказа (`Order`) и персистентность в PostgreSQL через SQLAlchemy 2.0.
2. Реализация детерминированной машины состояний заказа (State Machine): валидация переходов, запрет неконсистентных мутаций, идемпотентная обработка повторных событий.
3. Реализация межмодульного контракта `IOrderService.create_order()`:
* Фиксация заказа в статусе `PENDING`.
* Вызов клиента платежного шлюза `IPaymentClient.init_payment()`.
* Сохранение полученных `payment_id` и `payment_url`.


4. Реализация сервисных методов обработки жизненного цикла заказа для смежных модулей:
* `handle_payment_succeeded`: перевод в `PAID` и атомарная постановка Outbox-задачи `PUBLISH_POST`.
* `handle_publish_succeeded`: перевод в `PUBLISHED`.
* `handle_publish_failed`: перевод в `REFUND_REQUIRED` и атомарная постановка Outbox-задачи `EXECUTE_PAYMENT_REFUND`.
* `handle_refund_succeeded`: перевод в `REFUNDED`.


5. Гарантия паттерна **Transactional Outbox**: запись доменного события/задачи в таблицу `outbox_tasks` строго в рамках единой ACID-транзакции с изменением статуса заказа.

### 1.2. НЕ входит в зону ответственности (Out-of-Scope)

* Логика Telegram UX, сборка диалогов и работа с Redis (зона ответственности `bot_ingress`).
* Низкоуровневые сетевые запросы к API Т-Банка, расчет токенов SHA-256 и сборка фискального блока `Receipt.Items` (зона ответственности `payment_gateway`).
* Конкурентная выборка задач из базы (`FOR UPDATE SKIP LOCKED`) и управление ретраями воркеров (зона ответственности `outbox_engine`).
* Отправка сообщений в каналы через Telegram Bot API (зона ответственности `channel_publisher`).

## 3. Модель данных и схема БД

### 3.1. DDL схемы таблицы `orders`

```sql
CREATE TYPE order_status_enum AS ENUM (
    'PENDING',          -- Ожидает оплаты пользователем
    'PAID',             -- Оплата подтверждена банком
    'PUBLISHING',       -- Задача взята воркером в публикацию
    'PUBLISHED',        -- Успешно размещен в канале (успешный терминал)
    'REFUND_REQUIRED',  -- Публикация провалена, требуется компенсация
    'REFUNDED',         -- Возврат средств успешно выполнен (терминал)
    'CANCELLED'         -- Отменен пользователем или истек таймаут оплаты
);

CREATE TABLE orders (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id BIGINT NOT NULL,
    target_chat_id BIGINT NOT NULL,
    amount_kopecks BIGINT NOT NULL,
    status order_status_enum NOT NULL DEFAULT 'PENDING',
    
    -- Контент поста (структура PostContentDTO)
    content_payload JSONB NOT NULL,
    -- Контактные данные покупателя (CustomerContactDTO)
    contact_info JSONB NOT NULL,
    
    -- Данные эквайринга
    payment_id VARCHAR(64) UNIQUE,
    payment_url TEXT,
    
    -- Идентификатор опубликованного сообщения в Telegram (при успехе)
    published_message_id BIGINT,
    
    -- Журнал возврата средств / причины сбоя
    refund_details JSONB,
    
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Индексы для оперативных выборок
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_status ON orders (status);
CREATE INDEX idx_orders_payment_id ON orders (payment_id) WHERE payment_id IS NOT NULL;

```

### 3.2. SQLAlchemy 2.0 декларативная модель (`models.py`)

class Base(DeclarativeBase):

    __tablename__ = "orders"

    id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), primary_key=True, default=uuid.uuid4
    )
    user_id: Mapped[int] = mapped_column(BigInteger, nullable=False, index=True)
    target_chat_id: Mapped[int] = mapped_column(BigInteger, nullable=False)
    amount_kopecks: Mapped[int] = mapped_column(BigInteger, nullable=False)
    status: Mapped[OrderStatus] = mapped_column(
        Enum(OrderStatus, name="order_status_enum"),
        nullable=False,
        default=OrderStatus.PENDING,
        index=True,
    )

    content_payload: Mapped[dict[str, Any]] = mapped_column(JSONB, nullable=False)
    contact_info: Mapped[dict[str, Any]] = mapped_column(JSONB, nullable=False)

    payment_id: Mapped[str | None] = mapped_column(
        String(64), unique=True, nullable=True
    )
    payment_url: Mapped[str | None] = mapped_column(Text, nullable=True)
    published_message_id: Mapped[int | None] = mapped_column(BigInteger, nullable=True)
    refund_details: Mapped[dict[str, Any] | None] = mapped_column(JSONB, nullable=True)

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False,
    )

## 4. Машина состояний (Order State Machine)

Жизненный цикл заказа строго регламентирован. Любая попытка несанкционированного перехода должна вызывать доменное исключение `InvalidStateTransitionError`.

### 4.1. Граф переходов состояний

```
                  ┌───────────────┐
                  │    PENDING    │
                  └───────┬───────┘
                          │
             ┌────────────┴────────────┐
             │ (успех оплаты)          │ (таймаут / отмена)
             ▼                         ▼
      ┌─────────────┐           ┌─────────────┐
      │    PAID     │           │  CANCELLED  │ (терминал)
      └──────┬──────┘           └─────────────┘
             │ (воркер берет в работу)
             ▼
      ┌─────────────┐
      │ PUBLISHING  │
      └──────┬──────┘
             │
     ┌───────┴────────────────────────┐
     │ (успешная отправка в канал)    │ (сбой отправки: исчерпаны ретраи / 403)
     ▼                                ▼
┌───────────┐                ┌─────────────────┐
│ PUBLISHED │ (терминал)     │ REFUND_REQUIRED │
└───────────┘                └────────┬────────┘
                                      │ (успех /v2/Cancel в Т-Банке)
                                      ▼
                             ┌─────────────────┐
                             │    REFUNDED     │ (терминал)
                             └─────────────────┘

```

### 4.2. Матрица допустимых переходов

| Текущий статус | Допустимый следующий статус | Инициирующее событие / Метод | Порождаемая Outbox-задача |
| --- | --- | --- | --- |
| `PENDING` | `PAID` | Вебхук успешной оплаты от банка (`CONFIRMED`) | `PUBLISH_POST` |
| `PENDING` | `CANCELLED` | Истечение TTL оплаты или отмена пользователем | — |
| `PAID` | `PUBLISHING` | Захват задачи воркером публикации | — |
| `PUBLISHING` | `PUBLISHED` | Успешный ответ Telegram API (`message_id`) | — |
| `PUBLISHING` | `REFUND_REQUIRED` | Ошибка публикации (бан, лимиты, крах после ретраев) | `EXECUTE_PAYMENT_REFUND` |
| `REFUND_REQUIRED` | `REFUNDED` | Успешный ответ эквайринга на отмену/возврат | — |

Повторный приход одинакового события (например, дубль платежного вебхука `CONFIRMED`, когда заказ уже в `PAID` или `PUBLISHED`) обрабатывается **идемпотентно**: операция игнорируется, повторные Outbox-задачи не порождаются, исключение не выбрасывается.

## 6. Реализация сервисной логики (Service & State Transitions)

### 6.1. Создание заказа (`create_order`)

1. Рассчитать стоимость размещения (в копейках) на основе переданного `target_channel_id`.
2. Сгенерировать новый `order_id = uuid.uuid4()`.
3. Сформировать DTO `InitPaymentRequestDTO` и вызвать платежный клиент: `await payment_client.init_payment(...)`.
4. В рамках транзакции БД:
* Создать инстанс `OrderModel` в статусе `PENDING`.
* Сохранить полученные `payment_id` и `payment_url`.
* Выполнить коммит.


5. Вернуть в модуль бота `OrderCreatedResultDTO(order_id=..., payment_url=..., amount_kopecks=...)`.

### 6.2. Обработка успешного платежа (`handle_payment_succeeded`)

Вызывается модулем `payment_gateway` при валидации вебхука `CONFIRMED`:

```python
async def handle_payment_succeeded(
    self, order_id: uuid.UUID, payment_id: str
) -> None:
    async with self.session_factory() as session:
        async with session.begin():
            # Блокировка строки заказа от параллельных гонок
            stmt = select(OrderModel).where(OrderModel.id == order_id).with_for_update()
            result = await session.execute(stmt)
            order = result.scalar_one_or_none()

            if not order:
                raise OrderNotFoundError(f"Заказ {order_id} не найден")

            # Идемпотентность: если уже оплачен или опубликован — ничего не делать
            if order.status in {OrderStatus.PAID, OrderStatus.PUBLISHING, OrderStatus.PUBLISHED}:
                return

            if order.status != OrderStatus.PENDING:
                raise InvalidStateTransitionError(
                    f"Недопустимый переход из {order.status} в PAID для заказа {order_id}"
                )

            # 1. Смена статуса
            order.status = OrderStatus.PAID
            order.payment_id = payment_id

            # 2. Атомарное создание задачи Outbox
            outbox_task = OutboxTaskModel(
                task_type=OutboxTaskType.PUBLISH_POST,
                payload={
                    "order_id": str(order.id),
                    "target_chat_id": order.target_chat_id,
                    "content": order.content_payload,
                },
                execute_after=datetime.now(timezone.utc),
            )
            session.add(outbox_task)
            # Транзакция коммитится автоматически выходом из контекста session.begin()

```

### 6.3. Обработка сбоя публикации (`handle_publish_failed`)

Вызывается модулем `outbox_engine` / `channel_publisher`, когда бот исчерпал лимит попыток или получил критическую ошибку прав (403 Forbidden):

```python
async def handle_publish_failed(
    self, order_id: uuid.UUID, error_reason: str
) -> None:
    async with self.session_factory() as session:
        async with session.begin():
            stmt = select(OrderModel).where(OrderModel.id == order_id).with_for_update()
            result = await session.execute(stmt)
            order = result.scalar_one_or_none()

            if not order:
                raise OrderNotFoundError(f"Заказ {order_id} не найден")

            if order.status == OrderStatus.REFUND_REQUIRED or order.status == OrderStatus.REFUNDED:
                return

            if order.status not in {OrderStatus.PAID, OrderStatus.PUBLISHING}:
                raise InvalidStateTransitionError(
                    f"Невозможно инициировать возврат для заказа в статусе {order.status}"
                )

            # 1. Смена статуса
            order.status = OrderStatus.REFUND_REQUIRED
            order.refund_details = {
                "failed_at": datetime.now(timezone.utc).isoformat(),
                "reason": error_reason,
            }

            # 2. Атомарное создание задачи Outbox на возврат средств через API Т-Банка
            outbox_task = OutboxTaskModel(
                task_type=OutboxTaskType.EXECUTE_PAYMENT_REFUND,
                payload={
                    "order_id": str(order.id),
                    "payment_id": order.payment_id,
                    "amount_kopecks": order.amount_kopecks,
                    "reason": error_reason,
                },
                execute_after=datetime.now(timezone.utc),
            )
            session.add(outbox_task)

```

## 8. Граничные сценарии и конкурентные гонки

### 8.1. Быстрый вебхук (Race Condition: Webhook опережает сохранение в БД)

* **Проблема:** Пользователь мгновенно оплатил заказ через СБП, вебхук `CONFIRMED` приходит на сервер быстрее, чем метод `create_order` завершил транзакцию сохранения заказа.
* **Решение:** Если в `handle_payment_succeeded` заказ по `order_id` не найден в БД, сервис не падает фатально, а повторяет поиск с экспоненциальной задержкой (3 попытки с шагом 500 мс). Если заказ так и не появился — логируется `CRITICAL` алерт.

### 8.2. Дублирование вебхуков от банка (At-least-once delivery)

* Т-Банк отправляет повторные вебхуки, если не получил мгновенный `200 OK`.
* Вызов `handle_payment_succeeded` защищен строгой проверкой текущего статуса под блокировкой `with_for_update()`. Если заказ уже находится в состоянии `PAID`, `PUBLISHING` или `PUBLISHED`, метод моментально выходит без создания дублирующей Outbox-задачи.

### 8.3. Изоляция транзакции Outbox

* Запрещено разделять сохранение нового статуса заказа и создание записи `OutboxTaskModel` на две разные транзакции. Обе сущности обязаны сохраняться в рамках одного вызова `session.commit()`. Это исключает состояние, при котором статус заказа изменился на `PAID`, а задача на публикацию потерялась из-за падения процесса.

## 9. Критерии приемки (Definition of Done)

1. **Архитектурная чистота:**
* Отсутствие прямых обращений к Telegram API и HTTP-клиентам внешних платежных систем. Все вызовы строго через инжектируемые интерфейсы `IPaymentClient`.


2. **Unit-тестирование машины состояний:**
* 100% покрытие тестами матрицы переходов: проверка валидных переходов и выбрасывание исключений `InvalidStateTransitionError` на невалидных (например, прямой переход из `PENDING` в `PUBLISHED`).


3. **Интеграционные тесты с реальной PostgreSQL (testcontainers / pytest-asyncio):**
* Тест атомарности: успешная запись заказа и задачи `outbox_tasks` в одной транзакции.
* Тест защиты от параллельных гонок: два одновременных вызова `handle_payment_succeeded` на один заказ создают ровно одну задачу `PUBLISH_POST`.
* Тест сценария компенсации: вызов `handle_publish_failed` переводит заказ в `REFUND_REQUIRED` и создает задачу `EXECUTE_PAYMENT_REFUND`.


4. **Качество кода:**
* Строгая типизация: прохождение `mypy --strict src/modules/order_domain`.
* Отсутствие предупреждений линтера: `ruff check src/modules/order_domain`.
